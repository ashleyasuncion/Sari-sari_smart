PROJECT OVERVIEW
--------------------------------------------------------------------------------
Sari-Sari Smart is a mobile-first daily business companion for traditional sari-sari
store owners. Refactored from an item-by-item POS system to a daily awareness tool
based on interview findings. Three pillars: Stock Tracker | Daily Cash Summary |
Utang Notebook.

ARCHITECTURE
================================================================================

Multi-Page Structure:
  - 11 HTML files, each with its own phone frame
  - Shared style.css for consistent theming
  - Shared app.js with page-aware initialization (switch/case per page name)

Navigation:
  - Bottom nav uses <a> tags for native page navigation
  - 5 main nav pages (home, stocks/inventory, sales, utang/debts, help) have bottom nav
  - Sub-pages (new_sale, add_product, new_debt, setting) have NO bottom nav
  - Sub-pages highlight parent nav tab via pageToNav mapping
  - Settings gear passes ?from=PAGENAME for smart back-button destination

State Management:
  - In-memory state object with full application data
  - localStorage keys: sss_settings, sss_products, sss_sales, sss_customers,
    sss_debts, sss_usedNames, sss_stockStatuses, sss_dailyEntries,
    sss_specificSales, sss_eodData
  - New state fields: stockStatuses, dailyEntries, specificSales, endOfDayData

Localization:
  - Two languages: English (default) and Filipino
  - data-i18n attributes on all user-facing text
  - applyLanguage() updates all text dynamically + refreshes all views
  - Translation dictionary with 100+ keys per language

Data Flow (v2.2):
  1. User visits home → cards show real-time summaries of all data
  2. Sales page → enter gastos + kita → dailyEntry saved → home card updates
  3. Stocks page → tap to cycle status, Sold button to deduct → stockStatuses updated
  4. Specific sale → enter product name (autocomplete from inventory) + quantity
     → total auto-calculates as sellingPrice × qty → inventory directly deducted
  5. Specific sale → amount reflected in Today's Earnings on home (fallback if no daily entry)
  6. Specific sale → auto-creates debt if customer named
  7. End-of-Day → 3 steps → eodData saved → home card shows completion
  8. Settings → saved to state → applied immediately

  "Two pieces of bread worth 20 pesos, payment via GCash, split in half,
   the other half is cash."

The system would:
  1. Convert speech to text
  2. Use AI/NLP to analyze the intent
  3. Extract: product name, quantity, amount, payment method,
     debt information (if any)
  4. Automatically record the transaction

v2.51 — BACK BUTTON NAVIGATION FLOW FIX (HISTORY UNIFICATION)
Date: Aug 7, 2026
Status: DONE

Tracks: user reported the in-app back arrows don't follow
browser history: Inventory → Debts → New Debt, Back from New
Debt → Debts, but Back again → New Debt (loop) instead of
Inventory. Mobile was unaffected (NavController.popBackStack
on every screen). Investigation report delivered; user chose
"fix".

Root cause:
- Two conflicting back-arrow strategies. v2.23 (July 28)
  introduced historyBack() (referrer-checked history.back())
  but wired it to only 3 pages: debts.html, inventory.html,
  setting.html. The other 8 subpages kept hardcoded forward
  links (<a class="header-btn" href="X.html">): new_debt→debts,
  add_product→inventory, product_detail→inventory, restock→
  inventory, debtor_detail→debts, record_payment→debtor_detail
  (href set dynamically in renderRecordPayment), reports→morning,
  help→morning.
- A hardcoded back arrow PUSHES a new history entry; the page it
  lands on then POPS via historyBack() — so New Debt ↔ Debts
  bounced forever. (Trace: [inv,debts,new_debt] +link→
  [..,new_debt,debts] +pop→ [..,new_debt] → loop.)
- Secondary: historyBack() relied solely on document.referrer,
  which is empty on file:// / fresh-tab opens, sending those
  pages' back arrows to morning.html instead of the previous page.

Fix:
- 8 HTML files converted their hardcoded back-arrow <a href>
  links to <button class="header-btn" onclick="historyBack()">
  (same arrow SVG + button styling already used by debts/
  inventory/setting): new_debt, add_product, product_detail,
  restock, debtor_detail, record_payment, reports, help.
- record_payment.html: dropped id="rpBackBtn"; renderRecordPayment()
  no longer rewrites its href — back now always pops history
  (arriving from debtor_detail still returns to that debtor;
  arriving from the debts list returns to debts).
- app.js historyBack(): pops when the referrer is same-origin, OR
  the referrer is empty AND window.history.length > 1 (file:// /
  fresh-tab opens with in-app history). An external non-empty
  referrer never pops, preserving the v2.23 "don't leave the app"
  guard. morning.html fallback only when nowhere to go back to.
- app.js: saveNewDebt() and saveRecordPayment() now use
  window.location.replace() for their post-save redirects so Back
  after saving skips the just-exited form (matches mobile
  popBackStack semantics; no more revisiting an exited page).
- All 11 back-arrow pages now use one uniform strategy.

Validation:
- node -c app.js -> SYNTAX OK
- grep: zero hardcoded back-arrow hrefs remain; rpBackBtn removed
- Node simulation of the exact reported flow: OLD -> loop
  (2nd back = new_debt); NEW -> debts → inventory → morning
  fallback, no loop; record_payment back -> debtor_detail
  (specific-debtor behavior preserved)
